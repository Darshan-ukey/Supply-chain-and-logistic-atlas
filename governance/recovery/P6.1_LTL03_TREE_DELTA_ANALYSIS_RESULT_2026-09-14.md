## Deterministic generator rule corrections

### R1 — Seed-preservation rule
Treat each `workDecompositionSeed` entry as one primary work unit in source order. Do not split it merely because its wording contains multiple nouns, objects, verbs or conceptual substeps.

### R2 — Child-contract evidence threshold
Recursively split a primary work unit only when frozen governed source contains at least two distinct child-level execution-significant contracts, each independently supportable by source evidence. A child contract requires its own operation/gate semantics and enough source support to evaluate terminal status. Object-model membership alone is insufficient.

### R3 — No lexical/object-model decomposition
Do not create child work units solely from:
- canonical object children;
- field families;
- evidence-list items;
- workflow sequence adjacency;
- conjunctions in a source sentence;
- generic validation categories;
- source-claim names.
These may enrich a unit but do not independently prove a separate work unit.

### R4 — Source-only readiness proof
Classify a leaf from the pinned pre-generation sources only. Generated `trigger`, `atomicActions`, `decisionGates`, `evidenceRequirements` or `outputState` fields may make existing source semantics explicit, but cannot supply a missing semantic dimension. Every required V1 terminal-test dimension must trace to source or to a permitted deterministic derivation from source truth.

### R5 — Structural inference is not operational knowledge
Sequence-derived statements such as “after WD-X” may establish ordering/pre-state but cannot establish missing decision thresholds, authority precedence, validation logic, success/failure criteria, exception routing or semantic meaning.

### R6 — Missing child-level semantics fail closed
If a source seed step is execution-significant but the source does not provide enough detail for the V1 terminal test, keep it as a terminal blocker unless source-backed child contracts genuinely exist. Do not expand a vague parent into several apparently precise ready children.

Use `BLOCKED_BY_KNOWLEDGE_GAP` for missing canonical semantics, decision criteria, authority precedence, validation criteria, success/failure criteria or exception logic.
Use `BLOCKED_BY_CLIENT_BINDING` only where canonical work is understood and the unresolved value is enterprise/client/site/runtime configuration or mapping.

### R7 — Binding dependency propagation
A downstream operation that cannot be performed until a required client binding exists must not be labeled unconditionally ready merely because the mechanical action after binding is obvious. Either:
- represent the binding gate and conditional downstream child only when source supports that decomposition; or
- keep the primary unit blocked by client binding.
Avoid inflating ready counts with post-binding mechanical actions.

### R8 — Validation specificity rule
A generic source statement such as “run field/cross-field/cross-object validation” is not sufficient to create multiple ready validation leaves unless the frozen source also defines the actual validation rule(s) for each leaf. Known explicit rules/claims may be executable; unspecified validation families remain knowledge gaps.

### R9 — Conflict/authority rule
“Resolve by declared authority/source-of-truth policy” does not make conflict resolution ready if the governing precedence/policy is absent. Missing canonical precedence is a knowledge gap. Do not create a ready conflict-resolution action whose correctness depends on an unavailable policy.

### R10 — Historical-count non-target rule
Historical 43/37/14/8/15 is independent validation evidence only. The generator must never branch, merge or classify in order to hit those counts. After regeneration, compare naturally produced counts and investigate any delta semantically.
