The frozen Contract §4 lists `entryConditions`, `branchTransitions`, `temporalConstraints`, `evidenceRequirements`, `dependencies`, `outputState`, `fallbackIfBlocked` as fields a unit **"MAY also carry" "when applicable"** — not mandatory presence on every leaf. ## 3. Answers to the handoff's specific questions

**Is the 20-step `workDecompositionSeed` a primary spine that may only expand when distinct child-level execution contracts are independently source-supported?**
Yes — confirmed as a real, named, 20-item source field this round (not previously verified by either analysis). CR1/CR2 encode this directly.

**When does object-model or workflow detail justify a child unit versus remain detail inside the parent?**
Only when the detail describes a *second, independently evaluable* operation/gate with its own terminal-status-sufficient source support (CR2). Naming multiple canonical objects, fields, or workflow-adjacent steps is enrichment of the parent, not grounds for a child.

**Can sequence/order ever supply a trigger/pre-state? Under what condition?**
Yes, narrowly — CR3: ordering/pre-state only ("this runs after step N"), never decision criteria, authority, validation logic, success/failure, or exception routing.

**How must knowledge gaps/client bindings propagate through a composite and its children?**
Per CR6: a binding/gap at the parent blocks the parent; a child may only be separately represented (and separately readied) if source itself supports that specific decomposition. Otherwise the whole composite stays blocked.

**When are validation/conflict/HITL concepts too generic to be ready? What fail-closed rule applies?**
CR7 (validation) and CR8 (conflict/authority): generic category names without the actual rule/precedence in source → `BLOCKED_BY_KNOWLEDGE_GAP`.

**How is canonical authority/role proven without conflating it with runtime assignment?**
CR10 — the new rule this review adds, using real source (`exceptionPolicy`/`clientBindingPolicy`) rather than either inventing authority or requiring a runtime executor name.

**How are failure/alternate transitions and exception paths represented without mechanically requiring optional fields?**
CR11 — semantic sufficiency via either a leaf-level field or explicit reference to the real task-level `exceptionPolicy`, consistent with the Contract's "MAY... when applicable" language (§1 above).

**How should grouped-family language (DangerousGoods) constrain decomposition?**
CR2 directly: the source's own "one associated conditional object family, not independent universal fields" statement is exactly the kind of explicit constraint CR2 requires compilers to respect — this remains the clearest single violation in the current 64-unit tree (6 units where ~1-2 are source-supported).

**Which rules belong in the permanent compiler spec versus a manual-review checkpoint?**
CR1–CR9 are mechanically checkable against source structure (does a field exist, does a named source statement support a claim) and belong in the permanent spec. CR10 and CR11 involve a judgment call — *does this task-level policy genuinely cover this leaf's failure mode* — that I'd recommend as a required manual-review checkpoint the compiler surfaces rather than auto-resolves, consistent with how I already flagged the DangerousGoods "one family" language as needing a manual checkpoint in my original analysis.
