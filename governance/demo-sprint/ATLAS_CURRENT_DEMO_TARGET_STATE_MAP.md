> **Atlas owns understanding and specification. Downstream platforms own execution.**

Atlas is not another Malkom, ERP, TMS, workflow engine, RPA engine, BPM engine or digital twin. Those systems consume Atlas outputs.

# 4. TARGET DATA STORAGE MODEL

## 4.1 Canonical persistence
The backend **Knowledge Warehouse** is the canonical persistent store for governed Atlas knowledge/state.

HTML pages, Canvas views, JSON exports, WorkDefinition packages and runtime projections are **materialized views/derived artifacts**, not independent truth.

Supabase/runtime persistence may hold canonical governed runtime data, but GitHub remains canonical for source/tooling/schema/governance/version history and Drive remains durable governed evidence/custody where required.

## 4.2 Source custody
Authoritative-source records must retain:
- source identity and authority class;
- issuer/publisher;
- version/effective date;
- retrieval/custody location;
- source hash/snapshot identity where available;
- applicability/domain coverage;
- claims derived from the source;
- supersession/deprecation state;
- review cadence;
- provenance links to Atlas facts that rely on that source.

No source update silently changes Atlas.

## 4.3 Universe storage
Universe stores the durable cross-domain reference structure:
- domain hierarchy / A-level identities;
- cross-domain semantics;
- canonical identifiers;
- relationships/crosswalks;
- applicability and scope;
- version/supersession lineage;
- provenance to authoritative source coverage.

Universe is changed only when genuine universe-level evidence requires it. Daughter enrichment alone does not automatically trigger a new Universe version.

## 4.4 Daughter domain storage
Each daughter domain stores governed domain-specific reference work linked back to Universe identifiers:
- processes/tasks and applicability;
- actors/roles;
- domain objects/documents/information concepts;
- rules/constraints/regulatory context;
- states/events/outcomes;
- source-claim references;
- version/lineage;
- explicit unresolved knowledge and applicability boundaries.

A daughter module must never invent a new Universe identity merely to make downstream logic work.

## 4.5 Operational Knowledge storage
Operational Knowledge owns reusable knowledge required to understand how work should operate:
- business meaning/purpose;
- required information and information-resolution rules;
- requiredWhen / prohibitedWhen conditions;
- validations and controls;
- decisions and decision authority;
- expected outcomes;
- exceptions/escalations/recovery expectations;
- evidence/completion expectations;
- ambiguity/conflict/UNKNOWN state;
- source/evidence provenance;
- reusable client-binding requirements.

Operational Knowledge is upstream of decomposition. Missing knowledge should remain explicit rather than being fabricated downstream.

## 4.6 Canonical Work Decomposition storage
Store canonical work topology separately from runtime topology:
- parent A5 lineage;
- canonical child work units;
- work-unit semantic type;
- trigger/prerequisite/dependency;
- business-significant ordering/parallelism where governed;
- decomposition rationale/evidence;
- human/system boundary where it is a business semantic;
- exception/escalation/retry/recovery relationships;
- completion/evidence requirements.

Target stopping criterion is business-semantic sufficiency. Runtime-specific further splits belong to adapters/projections.

## 4.7 Canonical WorkDefinition storage
For each canonical work unit, store technology-neutral execution semantics:
- identity/version/lineage;
- applicability/prerequisites;
- inputs/objects/fields by canonical reference;
- rules/validations/controls;
- decisions and authority;
- permitted actions/system exchanges at technology-neutral level;
- HITL boundary;
- states/outcomes/transitions;
- waits/clocks/temporal constraints;
- exceptions/escalation/business retry/recovery;
- completion/evidence criteria;
- client-binding requirement references;
- execution characteristics that describe business behavior, not vendor implementation.

Do not store Malkom queues, BPMN service-task IDs, prompts/models, vendor configuration or credentials as canonical WD semantics.

## 4.8 Enterprise Context / Client Binding storage
Store enterprise-specific reality separately from reusable domain truth:
- actual systems/applications/systems of record;
- field/API mappings;
- customer/client masters and serviceability/network data;
- client SLA/cut-off/threshold/policy values;
- role/authority mapping;
- exception routing/communication channels;
- client-specific rule/policy variants and precedence;
- local contractual/regulatory constraints;
- environment/security/access requirements without exposing secret credential values;
- optional workload/capacity/NFR context where required.

The same canonical Atlas domain can therefore bind differently to multiple clients.

## 4.9 Governed Specification Assembly — target candidate
If AR0.2 is approved, store only references/proofs, not duplicated business truth:
- exact scope membership;
- dependency closure;
- unresolved/unknown/conflicting/client-binding-required facts;
- readiness/blocker chain;
- version-closed handoff manifest referencing exact canonical/enterprise versions/hashes.

This is derived proof/packaging, not a competing semantic source.

## 4.10 Runtime Adapter / Projection storage
Adapters store target-specific translation and loss/capability assessment:
- target runtime/platform identity and capability profile;
- mappings from canonical semantics to native structures;
- semantic loss / unsupported capability findings;
- Malkom queue/subqueue/work-type projections;
- BPMN/workflow/agent/ERP/TMS/RPA projections as applicable;
- technical connector/runtime configuration;
- target-specific verification results.

Runtime projection assets are derived and reproducible. They may be regenerated when canonical/enterprise truth changes.

## 4.11 Observation / Evidence storage — target candidate
Where execution feedback is available, store:
- canonical/specification identity reference;
- execution instance identity;
- observed states/events/evidence;
- conformance/deviation classification;
- runtime measurements/outcomes;
- proposed knowledge gaps.

Observed runtime behavior can propose changes but cannot silently rewrite canonical knowledge.

# 5. TARGET GOVERNANCE / UPDATE PIPELINE

## 5.1 Source review cycle
Current source-review policy defines:
1. CHECK_ISSUER_VERSIONS
2. INGEST_DELTA_METADATA
3. COMPARE_PRIOR_SNAPSHOT
4. CLASSIFY_NEW_CHANGED_DEPRECATED
5. RUN_SOURCE_TO_ATLAS_COVERAGE
6. OPEN_GAPS
7. SME_GOVERNANCE_REVIEW
8. UPDATE_ATLAS_ONLY_IF_APPROVED
9. REGRESSION_TEST
10. PUBLISH_VERSIONED_SNAPSHOT

Routine cadence: six months, with early review for material releases.

## 5.2 End-to-end change propagation
Target update flow:

`Source change detected`
→ preserve source snapshot/version/hash
→ classify affected claims
→ impact-map Universe/daughter/OK facts
→ open gaps/conflicts
→ human/SME/governance review where required
→ approve canonical change
→ write new version to canonical warehouse + GitHub governed schema/artifact definitions
→ selective regeneration of daughter/materialized views
→ regenerate decomposition only where impacted
→ regenerate WorkDefinitions only where impacted
→ recompute client-binding/readiness/specification packages
→ regenerate affected runtime projections/adapters
→ run full regression/security/trace checks
→ publish new versioned snapshot
→ update UI projections
→ preserve prior version and rollback lineage.

No UI should be manually edited to create semantic truth. UI renders governed state.

## 5.3 Asset-custody checkpoints
Every governed implementation mutation uses:
- `PRE_CHANGE_BASELINE`
- `POST_IMPLEMENTATION_PRE_QA`
- `POST_QA_GOVERNED_STATE`

Each checkpoint records versions/hashes/lineage/tools/tests/runtime state and evidence. Historical frozen states are immutable.

# 6. TARGET UI MATERIALIZATION MODEL

The target UI should not contain independent hard-coded business meaning. It should materialize canonical data by layer.

## 6.1 Page 0 / Universe UI
Reads current approved Universe version from canonical persistence/register and renders:
- domains/A-level hierarchy;
- cross-domain relationships;
- availability/maturity of daughter domains;
- public-safe summaries.

## 6.2 Daughter domain UI
Reads the approved daughter module and linked operational knowledge to render:
- A3/A4/A5 structure;
- domain/process/task detail;
- objects/documents/information;
- source/provenance status according to access role;
- knowledge gaps/coverage where authorized.

## 6.3 Execution-depth UI
For a selected A5/task:
- resolve linked Operational Knowledge;
- resolve governed decomposition version;
- resolve canonical WorkDefinitions;
- display explicit UNKNOWN/BLOCKED state if any required layer is absent;
- never infer missing depth merely to complete the picture.

## 6.4 Enterprise/client view
When a client context is selected:
- overlay/bind enterprise-specific values without mutating reference truth;
- show unresolved bindings/gaps;
- compute readiness/specification state where approved architecture supports it.

## 6.5 Adapter/projection view
For a selected downstream platform:
- render generated runtime projection;
- show lineage to canonical work/specification;
- show capability gaps/semantic losses;
- keep native runtime structures visually distinct from canonical Atlas structures.

## 6.6 Public vs protected UI
Public Atlas is a sanitized projection showing capability without exposing replicable execution IP.

Protected/admin Atlas may expose:
- detailed decomposition;
- WorkDefinitions;
- client-binding requirements;
- runtime projections;
- provenance/source detail;
- downloadable machine-readable contracts;
- readiness and governance evidence.

Role permissions remain separate from semantic governance.

# 8. DECISION RULE FOR EVERY DEMO CHANGE

Before merging any demo component, explicitly classify it:

- **KEEP** — already valid target architecture component.
- **BUILD_ON** — reusable in target with incremental extension.
- **BRIDGE** — temporary interface allowing old and new assets to coexist; must have a removal/replacement condition.
- **REPLACE** — existing component remains for rollback/history but target needs a different implementation.
- **RETIRE_AFTER_PARITY** — preserve until target equivalent passes regression, then remove from active path.
- **DEMO_ONLY** — disposable proof component; never allowed to become canonical by accident.

No unclassified demo component may become part of the target Atlas V2 production baseline.
