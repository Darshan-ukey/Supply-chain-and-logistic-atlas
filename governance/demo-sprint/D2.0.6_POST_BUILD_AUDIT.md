## 2. Regression found and fixed

| Suite | main `58b14c7` | demo branch (before fix) |
|---|---|---|
| `v1.1.8-serverless-budget.mjs` | PASS | **FAIL** |
| `v1.1.8-api-router-smoke.mjs` | PASS | **FAIL** |

**Cause:** commit `ed7507c` (my D2.0.1 work) added `api/execution-depth-projection.js` as a
**ninth** top-level serverless function, violating the "exactly 8 consolidated routers"
invariant. The Vercel function budget was *not* exceeded (9/12), which is why it went unnoticed —
the violated constraint is architectural, not quota.

**Fix, in the architecture's own idiom — the test was not weakened:**
- removed the 9th function;
- registered the handler inside the existing `api/atlas.js` router;
- added rewrite `/api/execution-depth-projection → /api/atlas?action=execution-depth-projection`,
  matching the 29 existing rewrites.

8 routers restored; endpoint verified still returning 200 with real LTL-03 content through the
consolidated route. The rewrite is necessary because the frozen renderer
(`assets/universal-daughter-renderer-v2.js`, hash-pinned in `canvas-2.0.1-candidate`) calls the
public path — editing that asset would break its registration.

## 6. MERGE-READINESS — two conditions, not blockers

The v1.1.8 release-integrity endpoint pins hashes for 37 critical files. Two now differ:

| File | Why it changed | Authorization |
|---|---|---|
| `data/module-catalog.json` | D2.0.2 catalog port (Road LTL 1.3 + Ocean 0.5 ACTIVE) | Owner-directed |
| `vercel.json` | D2.0.6 rewrite for route consolidation | this stage |

Both are intentional, evidenced changes — **not corruption**. The endpoint correctly reports
`criticalIntegrity: false` against the *v1.1.8* baseline, because the branch is intentionally
beyond v1.1.8.

**These pinned hashes were deliberately NOT updated.** Editing them to force a green result would
forge release integrity. Correct resolution is a release-baseline bump as part of a governed
release step, decided by the Owner.

Consequence for merge: merging to `main` without that bump means the live `/api/system?action=release-integrity`
endpoint reports `criticalIntegrity: false`. That is a real, predictable outcome to accept or
resolve deliberately — recorded here so it is not discovered post-merge.
