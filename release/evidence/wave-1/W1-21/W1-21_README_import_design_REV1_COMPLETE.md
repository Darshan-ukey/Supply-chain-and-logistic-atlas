## 4. Staging design (schema `atlas_stg_v73`; DDL in the staging_schema file plus REV1 PATCH, parsed OK with a PostgreSQL parser, NOT executed)
### 4.1 Identity and runs
`stg_release` (identity only from FROZEN_RELEASE_MANIFEST.json; CHECK on identity_source; the stale embedded block `supply-chain-logistics-universe-v7.2` is stored as evidence in `embedded_block_id`, never used as identity; G-050/IC-1). `stg_import_run` (operation id, extractor SHA-256, mode DRY_RUN/STAGE/READBACK/ROLLBACK, expected and observed counts, `authorization_ref` NOT NULL = W1-24 Owner record id).
### 4.2 Constructs and aliases
`stg_construct` is one typed registry for every V7.3 record (domain, lens, cycle, authority_rule, model, mode, role, node, movement, contract_ctx, context_rule, system, object, actor, event, document, relationship, exchange, destination). Columns carry `domain_ids`, `readiness_state` + `readiness_declared` (lens states 7/13/5/2 carried as declared, G-055), `claim_basis_class` (STANDARD_DEFINED, PROCESS_FRAMEWORK_ONLY, SPECIALIZATION, FUNCTION_LEVEL_SUPPORT, NO_BASIS, NOT_ASSESSED; G-058), `origin` (V73_SEED or GOVERNED_ADDITION), `seed_hash`. `stg_alias` is type-scoped (alias_norm + kind + id), which resolves the `dispatch`/`rma` cross-type overlap by construction (G-062); minting rules, duplicate gate and split/merge policy are W1-22's, this schema only provides the lineage kinds SPLIT and MERGE and the scoped alias key.
### 4.3 Relationships and dependency edges
`stg_relationship_type` (30 types, vocabulary v1.1, additive-only) and `stg_edge` (seed edges plus GOVERNED_ADDITION and DEPENDENCY_IMPACT edges with `criticality` LOW..CRITICAL). The 12 unused relationship types stay available, not pruned.
### 4.4 Sources, routes, versions, overrides
`stg_source` (67 SEED_GOVERNED rows + the 15 repo-only ids as CANDIDATE; CHECK: a REPO_V6_ONLY source can only be CANDIDATE; authority_class NOT_AUTHORITATIVE_UNTIL_ADMIN_APPROVED by default, SEED_BASELINE_DEC059 for V7.3 seeds, AUTHORITATIVE_ADMIN_APPROVED only with an approved request; tier 1-4 and `verification_status` per G-057/G-078). `stg_source_override` holds the two Owner-confirmed URL corrections (src-cmr, src-ecmr) with original, replacement, authority and `readback_result` (G-056/IC-6); the original URL stays visible. `stg_family_alias` holds otif, apqcFinance, uncitral as PROPOSED (uncitral is ambiguous between src-hague-visby/src-rotterdam and src-mletr/src-ncd; W1-23/Owner decide before CONFIRMED; G-053). `stg_source_route` is the construct-level link table (source -> domain/lens/cycle/placement group/regime/condition) with `route_basis`; assessor proposals are stored as ASSESSOR_PROPOSED_UNCONFIRMED and are excluded from routing views until approved (G-054: 13 unrouted sources, five W1-07 high-risk ones first). `stg_placement` stages 192 placements, 82 with route_class NONE (CHECK ties NONE to a null source). `v_source_entity_scope` is a VIEW labelled DERIVED_FROM_CONSTRUCT; entity-level source claims are never stored (granularity decision W1-11).
### 4.5 Lineage (source provision/version -> Atlas component)
`stg_source_version` (provision locator, version label, effective date, content hash, CURRENT/SUPERSEDED/CANDIDATE_DELTA) and `stg_lineage` (append-only by trigger; kinds SEED_IMPORT, DERIVED_ROUTE, ALIAS_RESOLUTION, URL_OVERRIDE, OWNER_DECISION, GOVERNED_ADDITION, PROFILE_CORRECTION, SPLIT, MERGE, PROMOTION, ROLLBACK; every kind except SEED_IMPORT/DERIVED_ROUTE requires an approval_id by CHECK). ## 7. Process: load, approval, readback, promotion, rollback
### 7.1 Load sequence (to be executed by W1-25 only after W1-23 PASS and W1-24 authorization)
1. Preflight (read-only): record row counts and a hash of column lists for all 29 public.atlas_* tables and the 18 migration versions; confirm schema atlas_stg_v73 does not exist; confirm the frozen HTML SHA-256; confirm `authorization_ref`.
2. DRY_RUN: run the extractor, produce expected counts and canonical hashes, no DB write.
3. STAGE: create schema, tables, views and functions in one migration (named for W1-25); load by `run_id` in dependency order (release, run, constructs, aliases, relationship types, edges, sources, overrides, family aliases, routes, placements, profile, roles, options, packs, anchors, subcapabilities, gaps).
4. GOVERNED_ADDITIONS are loaded as `stg_change_request` rows in approval_state PENDING and applied only after an approval row (7.3); seed rows load without change requests because they are the frozen record.
5. READBACK: run T-01..T-28 (section 10); store results in `stg_closure_evidence`; set the run to READBACK_PASS or READBACK_FAIL.
### 7.2 Identity and idempotency
Run id is the operation identity; every row carries `run_id`; re-running the same extractor on the same SHA produces identical `seed_hash` values, so a repeat run is detected (T-03) and refused unless rolled back first.
### 7.3 Human-in-the-loop approval and admin approval hooks (DEC-058 e; G-083; G-084 build deferred)
Every change-candidate (source admission or change, URL override, Universe candidate, daughter candidate, pack resolution, role/profile change, route assignment, promotion; `change_class`) is a `stg_change_request` carrying change class, scope (UNIVERSE or DAUGHTER; daughter changes are candidates only), before and after state, rationale, evidence pointer, rollback pointer, proposer, timestamps and `approval_state` PENDING / APPROVED / REJECTED / SUPERSEDED. A `stg_approval` row records approver identity, approver role (a field referencing `stg_admin_role`; seed role OWNER_ADMIN = the Owner until other roles are defined), decision, timestamp and a `change_hash`; apply refuses on a hash mismatch (stale approval). The proposer is NEVER the approver, with no exempt role (trigger `stg_approval_guard`). A candidate is not operative while PENDING: `stg_apply_guard` refuses APPLIED unless APPROVED, and `stg_operative_guard` refuses source authority `AUTHORITATIVE_ADMIN_APPROVED` and pack state RESOLVED without an APPROVED request on the same key. V7.3 seed sources load as `SEED_BASELINE_DEC059` (authority by DEC-059, not by this pipeline); the 15 repo-only ids and any found source load as CANDIDATE / NOT_AUTHORITATIVE. Everything consequential in this design (governed additions to roles, profile, packs, constructs, lineage; route assignments for the 26 unrouted entities and 13 unrouted sources; pack resolution; source admission; every promotion) goes through this table. `admin_notified_at` is a nullable hook for the later notification build; the queue UI, dashboard, notifications and extra admin roles (G-084) are NOT built and no task is created. The Product Definition and Architecture Registry tabs were not edited (Owner flag in G-083).
### 7.4 Promotion (reserved interface; NOT authorized by W1-21)
Staging is not the live Universe. A later Owner-approved task would map `stg_construct` -> `atlas_knowledge_entities`, `stg_edge` -> `atlas_knowledge_relationships`, `stg_source` -> `atlas_evidence_sources`, routes and versions -> `atlas_knowledge_evidence_links`, `stg_gap` -> `atlas_knowledge_gaps`, using a `knowledge_generation_runs` row for the run. That mapping is an assumption from column lists only and must be re-checked against the atl_123 contract (OQ-3). Promotion needs per-promotion approval and its own rollback by run id.
### 7.5 Rollback
- Staging level: all objects live in `atlas_stg_v73`. Rollback = (1) export the schema contents to an evidence file with SHA-256 for the audit record; (2) verify by `pg_depend` that no object outside the schema depends on it; (3) `drop schema atlas_stg_v73 cascade`; (4) re-run preflight comparison: the 29 public.atlas_* tables, their row counts (all 0) and the 18 migration versions must equal the preflight snapshot (T-18/T-19); (5) record a ROLLBACK event in the workbook ledger. The migration is accompanied by a down script containing exactly step (3).
- Row level (partial failure mid-load): every row has `run_id`; a failed run is deleted in reverse FK order by run_id, except `stg_lineage` which is append-only, so a mid-run failure of any run that reached lineage rolls back with the schema drop (step above), not row deletes.
- Governed addition rollback: a change request APPLIED is reversed by a compensating change request (applied_state ROLLED_BACK, lineage ROLLBACK) approved like any other.
- Promotion rollback (when authorized): delete by promotion run id from the kernel tables; their pre-promotion state (empty) is recorded in preflight.
- No rollback ever touches V7.3, the frozen manifest or any existing atlas_* table.
