Malkom Command · Domain Warehouse Engine · v2.3

Preserve the domain truth. Add execution intelligence. Project only what Malkom needs.

v2.3 makes the Road LTL V1.2 source model lossless inside the canonical Domain Warehouse contract. The complete source execution record, graph, ontology, applicability, actors, systems, evidence and provenance are retained unchanged; work decomposition and Malkom managed-work structures are added beside them. The Malkom adapter then projects only the structures supported by the current Malkom 3.0 architecture. Unsupported future capabilities are documented rather than forced into the current engines.

01 · Target

Domain Warehouse

A governed, per-domain library whose canonical record is a lossless superset of the governed source model. For Road LTL, every V1.2 source semantic is retained before any Malkom-specific decomposition is added. Malkom Command is the first runtime integration; the canonical definition remains reusable for other execution technologies and domains.

1canonical WorkDefinition per task/version
3primary Malkom material types: QueueTemplate, LifecycleTemplate, ValueList
22Road LTL ACTIVE task definitions · lossless source-linked
0required changes to existing Malkom 3.0 engines for v2.3 scope
Operating principle: source semantics are never overwritten by projection semantics. Domain Warehouse knowledge is richer than any one runtime schema. Canonical execution knowledge is stored once; runtime adapters project only the structures supported by the target execution technology. For Malkom, that projection includes queue/subqueue/work-type/schema/lifecycle/value-list structures while the richer execution contract remains available for Atlas inspection, transformation intelligence, documentation, AI grounding and testing.

Canonical definition

Domain execution semantics, source/provenance, work logic and reusable patterns remain independent of any one execution platform.

Client reality

Bindings map canonical fields/systems/statuses/routes/SLA/policies; extensions hold legitimate client-only work paths without mutating the canonical definition.

Malkom adapter

Projects the managed-work representation into QueueTemplate, LifecycleTemplate and ValueList, then materializes through the existing Command path.

Runtime adapter pattern

MALKOM COMMANDWORKFLOWRPARULES ENGINEAPI / SYSTEMDOCUMENT AIAI AGENTHUMAN-IN-LOOP
Architecture rule: Malkom is the first adapter, not the boundary of the Domain Warehouse. Domain knowledge changes by domain; client reality changes by client; runtime representation changes by execution technology.
v2.3 lossless rule: the source record is immutable and complete. Work decomposition, canonical execution fields and Malkom projection fields are additive layers with their own provenance. A queue name, work type, Malkom outcome or runtime limitation may never replace the original Road LTL task meaning, state, event, evidence, system authority, graph relationship or applicability rule.

07 · Queue Flow Explorer

See the compiled Malkom queue move

A queue can generate its own process map directly from the Malkom-facing projection: subQueues[].outcomes, outcome, route, status and next step. Nobody maintains a second diagram. The same queue graph can be rendered as BPMN for analysts or as a simpler flow view for general users, animated path by path, and exported as an image or BPMN 2.0 XML.

Built, not drawn

Core derives the graph from the queue projection and enumerates every valid start-to-end route. Changes in queue data redraw the map automatically.

Two views, one graph

BPMN renders start/task/gateway/end semantics. Flow renders the same graph as simpler operational blocks. Representation changes; semantics do not.

Portable output

Export the current view as an image and export standards-based BPMN 2.0 XML for use in BPMN-capable tooling.

Boundary: Queue Flow Explorer is a Malkom runtime/projection insight. It does not become part of the canonical WorkDefinition and it does not replace or clutter the Atlas spatial canvas. The canonical definition remains executor-neutral; this explorer visualizes what the Malkom projection can actually represent.

BPMN view: ○ start · ▭ subqueue/task · ◇ outcome gateway · ◎ end. Flow view uses the same graph with simplified blocks.
Loop handling: STAY is represented as a return edge rather than a terminal path. Path enumeration must use loop guards (for example maximum node visits / maximum depth) so “all combinations” means all finite valid routes, not an endless traversal.

14 · Build order

Embed / ingest the exact governed Road LTL V1.2 normalized model and verify its source hash, graph, transitions, ontology, applicability and source references before any projection logic runs.

Seed the Road LTL domain pack.

Load the 22 ACTIVE Road LTL WorkDefinitions, compile their Malkom projections into Raw Materials and prove they assemble through the existing downstream path without special-case code.

Add the UI seams.

Domain Warehouse authoring/inspection, Pull from Warehouse, Work Types editor and lifecycle assembly action. Atlas can expose WorkDefinition through Inspector/Transform without turning the canvas into an admin screen.
