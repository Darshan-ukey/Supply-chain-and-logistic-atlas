The Handover Protocol

An exception is not a status. It is a timed transfer of obligation between two parties, and it is not finished when the second party answers — it is finished when the first party accepts. Everything below follows from that one sentence.

01

An exception is an obligation with a clock on both ends

An offshore processor cannot finish an invoice because the work order was never updated. She raises a query. Onshore updates it and answers. She applies the answer and closes. Two people, two obligations, two deadlines — and only one of them is measured today.

Most exception systems model that as a ticket: one record, one queue, one clock, closed by whoever answered. That model is wrong here, and the wrongness is not academic. It produces the argument that every offshore/onshore pair has every month — your team is slow against no, you sat on our answer for two days — and neither side can prove anything, because the system only ever recorded one duration and gave it one name.

The unit this engine manages is a handover: a named question, raised by one party against a specific piece of work, owed by a second party, with a deadline on the answer and a deadline on what happens after it. Two clocks. At any instant exactly one runs. The engine's whole job is to know which, and to be able to prove it later.

None of that is particular to accounts payable, or to an offshore team. It is the structure of any bilateral obligation against a shared object — which is what a construction RFI, a clinical data query, a discovery request, a specialist referral and a reviewer's revision request all are. §17 sets out eight industries that arrived at this same shape independently, what varies between them, and why every one of those variations is a configuration axis rather than a different engine. The offshore invoice is the worked example throughout this document because it is the case in front of us; it is not where the model comes from.

The identity everything else hangs from

age = ownedMinutes(originator) + ownedMinutes(resolver) + pausedMinutes

Every term is attributable to a party and a reason. No term is a residual. If a system cannot produce this decomposition, it cannot answer the only question anybody actually asks about a stuck transaction.

Three things that are not the same

These get collapsed constantly, and collapsing them is what makes reports untrustworthy.

ConditionWho owes somethingClockEnds when
Hold — parking, on ice
unilateral		 Nobody. The holder chose to stop. Ages, but breaches nothing. The holder resumes.
Handover — the query
originator resolver		 A named counterparty, by a named time. Two, alternating. One runs. The originator accepts or withdraws.
Referral — outside the system
external		 A party with no seat and no SLA you control. Both internal clocks pause; a bounded referral clock runs. A response is recorded, or the bound expires.

The source architecture folded holds into handovers ("parking is normally a waiting condition inside a case"). That is a judgement presented as a fact, and it costs you the ability to report on self-inflicted delay separately from counterparty delay — which is the difference between a staffing problem and a supplier problem.

02

Twelve things the runtime's query cannot do

malkom-runtime already has a query. It is TaskQuery in packages/db/prisma/schema.prisma, driven by four routes in apps/server/src/modules/workflow/lifecycle.ts, surfaced at /queries. It is roughly forty lines of model and it is honest about being a first pass. Here is precisely where it runs out — this list, not a legacy blob parser, is the engine's requirements document.

GapWhat the code does todayWhat it costs
No resolver A query has askedBy and no destination. GET /api/workflow/queries gives an admin everything and everyone else only task.allocatedTo = self. The onshore person who must answer does not hold the task, so they cannot see the question at all. The Query Desk is a supervisor's list, not a work queue. This one gap makes the other eleven academic.
No reasonquestion is free text; no category, no code. Nothing to route on, group on, count, or write a rule against.

No return legansweredAt ends the record. Time the originator spends sitting on an answer is invisible. Half the delay is unmeasured.
One round if (query.status !== "OPEN") return 422. An inadequate answer cannot be pushed back. You raise a second, unrelated query and lose the thread — so round-trips, the best quality signal you have, cannot even be counted.
CLOSED is unreachable The comment documents OPEN | ANSWERED | CLOSED. No code path ever writes CLOSED. Acceptance does not exist. The resolver's answer is treated as the end of the matter.
State collision Raising sets state = "QUERY" unconditionally; answering the last open query sets state = "INDEXED" unconditionally. A parked task that raises a query silently stops being parked, and comes back as INDEXED. parkedReason survives; the state it explained does not.

The one thing to keep

The agentic answer path — an answer fills the field it was asked about, at confidence 1, because a person said so, and the pipeline picks the case back up. That is exactly right, and §8 generalises it from an agent special case into how every reason works.

04

The baton: two parties, two clocks, one running

At every instant a handover has exactly one holder. The clock that accrues is the holder's clock. Passing the baton stops one clock and starts the other in the same transaction, as one event, with no gap and no overlap.

Two roles, not two people, and not a hierarchy: originator is the party that raised it and must accept it; resolver is the party that owes the answer. Which of them is the senior one differs by domain and the engine has no opinion about it. Each role names a side, and a side may be a chain — an architect who forwards an RFI to a structural engineer has moved the holder without changing which side owes the answer, so the responding side's clock continues across the forward. That is the same rule as §6's reassign, applied one level up.

The state that makes it work

{
  holder:        "RESOLVER",          // ORIGINATOR | RESOLVER | EXTERNAL | NONE
  round:         2,                    // incremented on every re-query
  accrued: {
    originator:  "PT3H50M",          // closed segments only
    resolver:    "PT4H10M",
    paused:      "PT1H40M"
  },
  runningSince:  "2026-08-20T09:14:02Z", // null while paused or terminal
  dueAt:         "2026-08-20T13:00:00Z", // the CURRENT holder's deadline
  budget: {
    respond: { minutes: 240, calendar: "onshore-houston" },
    act:     { minutes: 480, calendar: "offshore-kolkata" }
  }
}

accrued holds closed segments only; the live figure is accrued[holder] + businessMinutesBetween(runningSince, now, calendar[holder]). Elapsed time is derived, never stored — which is what makes a replay of the event log reproduce the projection exactly, and what stops a clock from drifting when a process restarts.

05

Two calendars, one query

The response clock runs in the resolver's working hours. The action clock runs in the originator's. If a handover engine uses one calendar for both, every SLA it reports about a cross-shore pair is wrong, and wrong in a direction that flatters whichever team wrote the config.

The metrics engine already ships versioned calendars — timezone, workweek, working hours, holidays, DST policy — and a businessMinutesBetween derive that pins the calendar version it was validated against. The exception engine does not reimplement any of that. It reads calendars through a CalendarProvider port whose first-party adapter is @malkom/metrics-core, and whose in-memory default is a plain 24×7 calendar so the engine still stands up alone.

Consequence to design for, not around

With no overlap, a bad question costs a day and a badly-answered one costs two. Everything in §8 and §9 — reason forms that make one round sufficient, deflection before creation, clusters that ask once for forty transactions — exists because of this figure.

06

The resolver answers. Only the originator closes.

This asymmetry is the whole difference between a handover and a ticket, and it is what the ticket-shaped design gets wrong. The party who answered is not the party who knows whether the answer was any good.

CommandWho mayEffect on the baton
raiseoriginatorCreates the handover; baton → resolver; response clock starts.
answerresolverRecords a structured answer; baton → originator; action clock starts. Does not close.
re-queryoriginatorRound + 1; baton → resolver; a fresh response budget with the previous one preserved.
acceptoriginatorTerminal. Applies the answer to the subject if the reason declares a mapping. Both clocks stop.
withdraworiginatorTerminal. The question is no longer needed. Counts against nobody as a resolution — it is a signal the raise was premature.
auto-acceptengineTerminal, after a configured window with no originator action. Stops onshore being held hostage by an offshore team that never looks. Always recorded as an engine act, never attributed to a person.
reassignresolverNo baton move. Work moves inside the holding party; that party's clock keeps running.
rerouteresolver adminBaton stays with RESOLVER; destination changes; the response clock continues. Rerouting is not a fresh start — it is a correction, and its frequency is a measure of the routing table's quality.
referresolverBaton → external. Both internal clocks pause under a bounded referral budget.
escalateengine anyNo baton move. Adds a participant and notifies. Escalation buys attention; only a transfer moves work. Conflating the two is why escalation ladders stop meaning anything.
reopenoriginator adminFrom terminal, within a governed window, with a reason. Round + 1; baton → resolver. Counted separately from re-query: a reopen means the acceptance itself was wrong.
The two invariants worth failing a build over

1. No command may set holder = NONE except accept, withdraw and auto-accept — all three of which belong to the originating side. If the resolver can reach a terminal state, you have rebuilt a ticket. A domain where the originator genuinely owes nothing after the answer — a consumer service desk, say — expresses that by setting autoAccept to zero, not by letting the resolver close. The behaviour is identical; the measurement is not, because the originator's leg is still recorded even when it carries no budget.

2. No command may reset or reduce accrued[party]. Clocks are monotonic. Every workaround anyone has ever built to make an SLA look better lands on one of these two lines.

07

Commands in, facts out

Every mutation is a command; every command produces exactly one event and one updated projection, in one transaction, with an outbox row. Nothing is a shared mutable field — there is no comment column being appended to, and therefore nothing to parse later.

// COMMAND
{
  commandId:       "cmd_01JAV…",
  idempotencyKey:  "task:9001|field:costCentre|reason:COST_APPROVAL|r2",
  caseId:          "qry_01JAT…",
  expectedVersion: 7,
  type:            "handover.answer",
  actor:  { id: "usr_42", party: "RESOLVER" },
  data:   { decision: "approved", approvedAmount: "1840.00 USD",
             approverRef: "WO-88213/rev4" }
}

// EVENT — appended, never edited
{
  eventId:   "evt_01JAV…",
  type:      "handover.answered.v1",
  sequence:  8,
  baton:     { from: "RESOLVER", to: "ORIGINATOR",
               closedSegment: { party: "RESOLVER", minutes: 168,
                                calendar: "onshore-houston@v3" } },
  policy:    { generation: 41, reason: "COST_APPROVAL@v6",
               routing: "rules:grp_7c2@v11" },
  actor:     { id: "usr_42", snapshot: { name: "…", unit: "AP Houston" } },
  data:      { … }
}

Two details in that event carry disproportionate weight. closedSegment means the clock arithmetic is done once, at the moment of truth, by the process that held the lock — not recomputed later by a reporting query that may disagree. And policy pins the exact reason version, routing group version and calendar version, so a case worked in March can still be explained in November after all three have changed.

Writes require Idempotency-Key and If-Match. A conflict returns the current version and a machine-readable code; clients re-read rather than overwrite. The CLI is a pure REST client, and buildFetchHandler(engine) returns a web-standard handler a host can mount on its own server — the same two conventions every Malkom engine already follows.

08

A reason is a contract for an answerable question

Free-text questions are why round-trips happen. If a reason cannot state what it needs, what a valid answer looks like, and what happens to the answer, it is a label — and labels route nothing, measure nothing and improve nothing.

reason COST_APPROVAL @v6
  appliesTo    subject.type = invoice
                && subject.state in (INDEXED, PROCESSED)
                && field = fields.approvedCost

  asks         amount        money     required
                costCentre    string    required from valueSet:cost-centres
                justification text      min 20 chars

  answerShape  decision       enum approved | rejected | revised   required
                approvedAmount money    required when decision != rejected
                approverRef    string   required

  applyOnAccept  fields.approvedCost ← answer.approvedAmount  confidence 1.0

  budgets      respond 4h  calendar resolver
                act     8h  calendar originator
                referral max 3d

  blocking     true          // this field must be settled before the case closes
  clusterBy    workOrderRef  // one answer can settle many transactions
  deflectOn    (supplierId, costCentre) within 30d
  fourEyes     when answer.approvedAmount > 25000

Three of those lines do most of the work.

  • answerShape is what makes one round sufficient. A resolver cannot answer "will check" into a typed enum. The system asks a closed question and gets a closed answer.
  • applyOnAccept generalises the runtime's existing agentic behaviour — the answer fills the field it was asked about, at confidence 1, because a person said so — from one hardcoded path into how every reason works.
  • blocking is per reason, not global. A non-blocking question lets the case continue to the point where it genuinely needs the answer, which is the single cheapest throughput win in the whole design and the direct fix for gap 8.
Reason quality is a measurable thing

Rounds per query, grouped by reason, is a report about your reason catalogue rather than about your people. A reason averaging 2.4 rounds has a badly specified answerShape. That is a config change an author can make on a Tuesday, backtested against last quarter's real handovers before it goes live — which is a kind of improvement loop that a free-text queue structurally cannot offer.

09

The best handover is the one never raised

World-class exception management is judged on deflection and leverage, not on throughput. A queue that answers a thousand questions well is worse than one that never had to ask nine hundred of them.

Deflect
−1This exact question already has an accepted answer. Show it at raise time; nothing is created.
Cluster
40:1Forty invoices blocked on one work order. Ask once, accept forty times, each individually audited.
Dedupe
n:1A second raiser on the same subject, field and reason joins the open handover as a watcher.
Suppress
0A reason firing above its configured rate is an upstream defect, not a queue. Raise a problem record, stop opening cases.

Deflection is a lookup at the moment of raise, keyed by the reason's own deflectOn tuple, over accepted answers inside a window. The raiser sees the previous answer, who gave it, and when, and takes one of two paths: use it — in which case no handover is created and the deflection is counted, which is the most valuable number this engine produces — or raise anyway, in which case the engine links the new handover to the answer that was offered and rejected. That link is how you learn a "known answer" has gone stale.

Clustering is the honest generalisation of the legacy "update similar exceptions" bulk edit, and the important difference is when it happens. The legacy feature let you select rows afterwards and paste a shared remark. Clustering happens at raise time, from the reason's clusterBy key, so the cluster exists before the question is asked and one answer lands against all of its members. Each acceptance is still an individual command with its own authorization check, its own expected version and its own event — a bulk action that reports one aggregate success is a bulk action that hides its failures.

Suppression is the loop back into the process. Query rate per thousand transactions, by reason, is a process-capability signal in the statistical-control sense. A reason firing at four times its baseline is telling you something upstream broke — a master-data feed, a supplier's format, a rule that went live on Tuesday. The right response is a standing problem record and a suppression window, not a thousand individually-worked cases.

10

Escalation ladders, and the discipline of the pause

Escalation triggers on the fraction of the current holder's budget consumed, in the holder's calendar. Both parties escalate — an originator sitting on an answer escalates to their own lead, exactly as an unanswered question escalates to the resolver's.

Budget usedWhat happensWho it reaches
80%At-risk flag on the case and on its worklist row.The holder.
100%Breach event. The clock keeps running — a breached handover is still owed.The destination's lead, in that destination's calendar.
150%Second rung. Case pinned to the top of the desk.The process owner for the reason.
ConfiguredThird rung, by reason severity only.Named role, resolved through the directory at fire time — never a stored person.

Rungs are roles in calendars, not people. A ladder that names an individual breaks the week they take leave, which is reliably the week you need it.

Every pause is named and bounded

An unbounded pause is the most common way an SLA regime quietly becomes a lie. The engine will not allow one:

  • A pause requires a pauseReason from the configured catalogue. There is no free-text pause and no boolean flag.
  • Every pause reason carries maxMinutes. At the bound the engine resumes the clock itself and emits handover.pause-expired.v1. Nobody has to remember.
  • Paused minutes are reported per reason as a share of total age. If "awaiting supplier" is thirty per cent of your ageing, that is a procurement finding, and it should be legible as one.
  • The config verifier refuses to activate a generation containing a pause reason with no bound or with a bound past the case's own retention window.

Five engines already do most of this

The engine that gets built here should be small, because malkom-engines already contains routing with backtests, concurrency-safe claiming, lifecycle legality, business calendars and a metrics registry. Building a second copy of any of those inside this one would be the expensive mistake.

Open decision · the second clock

The workflow engine gives an item one clock. Two options. (a) Two workflow items per handover, one per leg — reuses everything, but the two legs can drift and "the case" stops being one object. (b) The exception engine owns the baton ledger and asks workflow only is this move legal. I recommend (b): the alternating two-clock ledger is the one genuinely new mechanism here and it should live in one place, owned by the engine whose entire purpose is that mechanism. The cost is honest and worth naming — a second timing ledger exists in the product, and the two must never be asked the same question.

12

What it owns, and what it must never touch

The house rule across malkom-engines is the engine owns decisions, never your data. The rules and metrics engines never write a host table. Allocation writes exactly two columns, through a guarded claim, and says so loudly. The source architecture proposed twenty tables in the host schema, which is not an engine — it is a second application wearing an engine's name, and its own portability section contradicts it.

The engine ownsThe host ownsNever crosses
Handover aggregate, event ledger, baton segments, rounds, resolutions, links, clusters, deflection index, idempotency records, outbox. The subject — invoice, booking, shipment, claim. Identity and org units. The authorization decision. Attachment bytes. Notification delivery. Business payloads and evidence bytes stay client-side. Command receives approved aggregates and health, never case content.

Storage

Engine state lives in SQLite through Node's built-in node:sqlite — same as its five siblings, zero native modules, no broker. A Postgres adapter behind the same HandoverStore port is a first-party option for hosts that want the ledger beside their own data; it is an adapter, not the definition. The public surface is the versioned command, event and config contract. Table names are not API.

Ports

HandoverStore · UnitOfWork · SubjectResolver · Directory · Authorizer · Clock · CalendarProvider · RoutingAdvisor · AllocationPort · EvidenceRef · NotificationIntent · EventPublisher · Logger

Every port has an in-memory default, so npm i @malkom/exception-core and eight lines gets you a working handover with a 24×7 calendar and first-available routing. First-party adapters then swap each default for the corresponding Malkom engine, one at a time. That progression — works alone, better composed — is what makes an engine adoptable by a host that has never heard of MALKOM.

13

Configuration is proven before it can govern work

Reason catalogue, routing, budgets, calendars, pause reasons, escalation ladders, forms and the noun vocabulary are drafted in Command, verified, backtested, approved by a second person, frozen into a numbered generation, and applied to UAT before a byte-identical promotion to production. The runtime's ApprovalRequest model already carries this shape — domain, entityType, payload, currentState, four-eyes enforced in the approvals module — so this engine adds a domain, not a mechanism.

What the verifier refuses

  • A reason whose answerShape omits a field that applyOnAccept reads.
  • A route resolving to a destination with no eligible members in the directory — a queue nobody can see is a black hole, and it should fail at the belt, not at 2am.
  • A budget in a calendar that does not exist, or that no longer has that version.
  • A pause reason with no bound, or a bound outside the case retention window.
  • An escalation rung naming a person rather than a role.
  • A clusterBy key that is not a declared field on the subject type.
  • A change that would leave a live handover pointing at a retired reason version — retired definitions must stay loadable for cases still open under them.
  • Two same-priority routing rules producing contradictory destinations for one test case.
Simulation is the part worth insisting on

Because routing runs through the rules engine, a proposed change is replayable against real historical handovers before approval: this changes the destination for 312 of last quarter's 4,180 queries, 287 of them COST_APPROVAL out of Houston, and it moves 40 hours of answering onto a desk with four people. That sentence is the difference between governance and a change-approval ritual, and no part of it requires anything this platform does not already have.

15

Raising from the case, not from a page

A handover is raised against a field, from the form where the work stopped. That single decision gives you the apply-on-accept mapping, precise blocking, real deduplication and an honest cluster key — all of which are impossible if the question starts life as a text box on a separate screen.

16

Every query on a transaction, and every transaction on a query

Four surfaces, and the ordering principle for each is whose clock is running, never when was it created.

On the case — a Handovers panel

Sits beside the audit timeline on TaskDetailPage. Grouped by state: with the resolver, then back with us, then settled. Each row carries reason, destination, holder, time on the holder's clock against budget, and round count. A row at round 3 reads differently from a row at round 1 and should look different.

On the worklist row — a badge

Open count, and whose clock. Coloured by party, flagged at 80% of budget. So the question "what of mine is waiting on someone else, and what is waiting on me" is answered by scanning a list rather than by opening thirty cases. Today it takes thirty clicks and the answer is still incomplete.

Before you raise — what already exists

The raise dialog shows open handovers on this subject, on siblings sharing the cluster key, and the deflection candidate. This is where duplicate suppression belongs: at creation, where it costs one glance, not in a cleanup sweep three weeks later where it costs a meeting.

The resolver's desk

The gap that makes the current implementation unusable from the onshore side. The desk is an allocation queue over destination, not a filter over cases the person happens to hold. Ordered by time remaining in the resolver's own calendar, clustered rows collapsed to one question with a member count, and the reason's answer form rendered inline — a resolver should be able to answer without opening the transaction, because the reason already gathered everything the answer needs.

Reuse, not new screens

All four surfaces are the table engine over one projection with different saved views. The runtime already renders lists and dashboards from generation-carried page definitions (7a0452e, 8bc2437), and definitions narrow what is shown without ever widening who may see it. The desk should be a page definition, not a bespoke React page — which also means a client can reshape it without a deploy.

The same protocol, invented eight times

A design that comes from one example is a description of that example. The check that matters is whether industries that have never heard of each other converged on the same structure — and whether the places they each stop short are the same places. They did, and they are.

ConstructionRFI Contractor → architect → RFI Manager closes. They built the baton and gave it a name. Procore carries a literal Ball in Court field that shifts to the assignee on open, moves again if they forward it, and returns automatically to the manager on response. Clinical trialsquery Data manager → site coordinator → data manager closes. Two-legged in law, one-legged in almost every piece of software that supports it.

What is common across all eight

A named question against a specific object; a counterparty who owes an answer; a deadline on that answer; an answer that is structured, not free prose; a party who decides the answer was sufficient; and rounds when it was not. Every one of those is in §4 through §8, and none of them came from accounts payable.

What varies — and therefore must be configuration, not code

AxisRange across the eightHow the engine expresses it
How many legs are budgeted Both (peer review, discovery), the answer only (service desk), the answer under statute and nothing after (trade finance). budgets.respond and budgets.act are independently nullable. An unbudgeted leg is still measured — see §18.
Direction The blocked worker asks the authority (AP, RFI). The authority asks the doer (EDC, customs, audit). Roles are structural, never hierarchical. originator means the party who raised it and must accept it — nothing about seniority.
How many parties Two, usually. Three when an RFI is forwarded, or when triage hands to a specialist. The holder is a reference into an ordered party chain, not a two-valued flag. A forward moves the holder without changing which side owes the answer, so the responding side's clock keeps running across it.
Who closes Originator (AP, RFI, discovery, healthcare, peer review) or resolver (service desk). Always the originator, with autoAccept as the window. Setting that window to zero produces the service desk's behaviour exactly, without weakening the invariant.

Importing the practices, with their reasons intact

Exception management is a mature discipline under a dozen different names. Almost nothing below needs inventing — it needs importing deliberately, with the reason it exists intact.

The one convention to refuse, and it is nearly universal

Ask any service-desk platform what to do while you are waiting on the requester and it will tell you the same thing: move the ticket to awaiting customer and pause the SLA timer. Every major tool ships that behaviour, and the standard advice is to use it deliberately to avoid breaching.

Why pausing is the wrong instrument

Pausing is what you do when you only have one clock and it belongs to the provider. It is not a measurement of the counterparty's time — it is the absence of one, dressed as a feature. Everything that happens during the pause becomes invisible: the requester's own delay, the ageing the customer actually experiences, and any obligation the requester was under.

This engine does not pause when the other party owes something. It starts their clock. Pause is reserved for the one case where it is honest — §1's referral, where a party outside the system holds the work and neither internal party owes anything — and even there it is bounded, because an unbounded pause is the same lie with a longer fuse.

The second near-universal convention to refuse: letting the clock reset when a ticket moves between groups. Together those two defaults are why cross-team SLA reporting is so widely distrusted, and §6's invariants exist to make both impossible.

Migration is small, because there is little to migrate

This is where I most differ from the source architecture. It plans a large forensic migration from an encoded comment blob — parser versions, confidence scores, delimiter defects. That work is real for the legacy invoice tool. It is not the work in front of this runtime, whose TaskQuery is a clean, thin, forty-line model with no encoding to reverse.

  1. Import every TaskQuery as a closed single-round handover: askedBy → originator, question → round-1 text under reason LEGACY_UNCLASSIFIED, answer → the round-1 answer, answeredAt → accept, with importedFrom: "TaskQuery" and the original row retained verbatim.
  2. Do not synthesise clock segments. Legacy rows have no calendar and no destination; inventing minutes for them poisons the first quarter of every report. Mark them clockUnknown and let every metric exclude them explicitly.
  3. Classify open rows by hand — there will be few — into the new reason catalogue, and route them.
  4. Run new commands into both stores behind a flag; reconcile counts, open sets and ownership.
  5. Move /queries to the new projection; retire the four lifecycle.ts routes; drop the state-collision behaviour of gap 7 in the same change.
  6. Rename /exceptions → Routing overrides, and take the word back.
Where the legacy forensics does apply

If the old invoice implementation is ever imported into a MALKOM deployment, §14 of the source artifact is the right playbook and should be lifted wholesale — retain the blob as immutable evidence, parse header lines only, record parser version and confidence, never rewrite the body. That is genuinely hard-won knowledge. It is just not on this critical path.

Ten decisions, and what I could not check

#DecisionWhy it is load-bearing
1The unit is a handover, not a ticket. Two clocks, one baton.Everything else follows. Reject this and the rest is a ticket system with extra tables. Eight industries reached this shape independently (§17), so it is the general structure of a bilateral obligation, not a description of an AP desk.
2The originator closes; the resolver may only answer.The party who answered cannot judge the answer. Auto-accept protects the resolver from an unresponsive originator.
3Clocks are monotonic; reassignment inside a party never resets one.The single most-gamed rule in the industry. Enforce it in the aggregate, not in review.
4Each leg runs in its own party's calendar.Figure 2. One calendar for a cross-shore pair produces confidently wrong SLA reporting.
5The noun is configuration. Runtime default query; the runtime's existing page becomes Routing overrides.Resolves a live collision permanently, and makes one engine serve query, break, referral and ticket without a fork.
6SQLite state, host tables untouched, Postgres as an adapter.The house rule every sibling follows. Twenty tables in the host schema is an application, not an engine.
7Routing is proposed by rules and always shown with its reason; overrides are events.Makes the routing table improvable instead of merely present.
8Clusters at raise time replace bulk edit.One answer, many acceptances, each individually authorized, versioned and audited.
9Every pause is named and bounded; the engine resumes the clock itself.Removes the standard route by which an SLA regime becomes decorative.
10Metrics are published as a registry entity; the engine ships no dashboards.Clients author SLAs where they author every other SLA, with backtests and calendars they already trust.
11A leg without a budget is still measured. 12Roles are structural, never hierarchical, and a side may be a chain.The authority raises in EDC, customs and audit; the blocked worker raises in AP and construction. An engine that assumes the raiser is junior gets half its addressable domains backwards.

Build the baton ledger first, before any screen, and prove the two invariants with property tests.
