Malkom Agent Engine

How we will build AI agents for Malkom. Agents are created in the Command. They run in the client runtime. This page answers every challenge you listed, in simple words.

Rule 1 — read this first

Agents are autonomous

This rule controls everything else on this page.

An agent gets a goal. It does not get a list of steps.

The agent looks at the case. It decides its own steps for that case. It decides which tools to use, in which order, and how many times. If it needs more information, it goes and gets it. If its first approach fails, it tries a different one. It decides on its own when it is finished, and when it is stuck.

Two identical cases can be handled in two different ways by the same agent. That is normal and correct. If the steps are fixed before the run starts, it is not an agent — it is a workflow. We do not ship workflows and call them agents.

We only define four things about an agent, and they are all limits, not steps:

  • Its goal — what a finished case looks like.
  • What it may access — which data fields and which tools.
  • What it may spend — time and money limits per run.
  • The four ways it can finish — done, question, handover, parked (explained below).

Inside those limits, the agent works however it decides to. This mix — free inside the limits — is what makes it safe to run autonomous agents on a customer's machine.

The full picture

Two sides, one flow

The system has two sides, and they stay separate:

  • The Command — agents are developed here, assembled into pipelines here, tested on the customer's UAT from here, put in the shop here, and shipped from here.
  • The client runtime — agents run here. Monitoring and observing also happens here, including which Integrations the agents use.

Work flows exactly as you described: email and EDI come in. The ML engine classifies the task to a sub-queue and extracts fields. The queue's agent pipeline takes it. Every case ends in one of the four endings. When an agent fails, the case goes to your HITL queue with the agent's work attached — the fields it filled, its confidence numbers, what it tried, and why it stopped. A person never starts from zero.

Challenge 01

Which framework?

You askedWhich agentic framework should be used for development?

We do not lock into one framework. Instead, the engine defines a small contract, and every framework connects to it through an adapter. To Malkom, an agent is three things:

  1. 1

    A manifest — one small file that states: the agent's goal, its queue, which fields it reads and writes, its tools, its rules, its limits, its telemetry settings. Limits only — never steps.

  2. 2

    A container — the agent's code, packaged. It can be written in Python, TypeScript, Go, or anything else. It can use LangGraph, CrewAI, PydanticAI, or plain code. Malkom does not need to know what is inside.

  3. 3

    A connection — one standard way to start the agent, one way for it to report what it is doing, and the four endings.

On day one we ship two ready adapters so developers can start fast: TypeScript and LangGraph (Python). Any other framework that follows the contract also works. In every framework, the agent inside is autonomous — the adapter passes the goal in and the endings out. It never controls the agent's steps.

Challenge 02

Full agent development, inside the Command

You askedFull agentic development capability, and it has to happen in the Command.

The Command gets an Agent Studio. Not a settings form — a place where agents are fully developed:

  • Start from a template. Pick a framework and a queue type. The studio creates a working autonomous agent you can then change — goal written, connection wired, telemetry already on.
  • A real code editor in the browser. You edit the agent's code directly, with the manifest next to it as a form. Every save creates a draft version. Every publish creates a numbered version. Git runs underneath automatically.
  • A run button. One click runs the draft on sample cases in a sandbox. You see every step and every tool call, live, while it runs.
  • The outside door also works. A developer who prefers their own editor can push code from there. It arrives in the studio as a draft version. Both paths lead to the same place.
  • Publishing puts it in the shop as "pending". It cannot reach a customer until it has passed testing (Challenge 04).

Creating, editing, testing and approving agents — all of it happens in the Command.

Challenge 03

The agent pipeline for a queue and its sub-queues

You askedDefining an agentic pipeline for a queue and/or its sub-queues. And how do agents for a queue speak to each other — connected agents?

On the canvas in the Command: pick a queue, place agents on it, draw the connections. A sub-queue can override the queue's pipeline — the same override pattern Malkom already uses everywhere else.

Agents speak to each other in two ways:

  • The shared case record. Every agent that works on a case writes its results onto the case — fields, confidence numbers, notes. The next agent sees all of it. Nothing is worked out twice. When a person gets the case in HITL, they see the same record.
  • Direct calls. An agent can call another agent in its pack when it decides it needs help — for example a rate-lookup agent. Which agent may call which is declared on the canvas. Whether and when to actually call is always the agent's own decision.

Important: the pipeline only defines connections between agents — who hands work to whom, who may help whom. It never defines the steps inside an agent. Inside, every agent follows Rule 1.

Challenge 04

Testing — on a running system, never in the workshop

You askedThe ability to test created agents directly on the customer's UAT runtime.

The factory that builds an agent never also judges it. The studio's run button is only a quick check while you build. Even that check runs on real plumbing — the same Integration pipes and the same pre-built MCP servers a live case would travel, never a hand-rolled fake. Real testing happens somewhere else: on a deployed, running client runtime.

Getting there uses the shipping line you already have. The assembled setup is committed and pushed by the Command's CI/CD — every customer has its own branch, with a UAT and a Prod. It lands on the branch, deploys to a UAT, and is tested there. Nothing reaches Prod until the Command's CI/CD approves it.

There are two running systems it can be tested on, and everything lands at the first before the second:

  1. 1

    Malkom's own UAT and Demo. Fully deployed client runtimes Malkom runs for itself. Whatever we build from the Command bears out here first — before it is ever pushed down to a customer.

  2. 2

    The customer's own UAT. The same setup, on the customer's own running system, only after it has proven out on Malkom's own.

On a running UAT — Malkom's or the customer's — the agent is tested three ways:

  1. 1

    Replay. Run on that system's past cases, where the correct answer is already known. Fast, cheap, sends nothing anywhere.

  2. 2

    Shadow. Run on real UAT traffic. The agent does the full work but delivers nothing — its access pass blocks every write, so it cannot change anything even if its code tries. Its answers are compared with what the people actually did. The most reliable test, because the traffic is real.

  3. 3

    Canary. A small share of live UAT traffic, handled for real. If the results get worse, it rolls back on its own.

Each run produces a scorecard: how often it was right, how fast, what it cost, where it failed. And one fixed gate, enforced by the Command's CI/CD: no scorecard on a deployed UAT = no promotion to Prod.

Challenge 05

The shop

You askedA shop of pre-developed agents per queue, to pick and choose and assemble for an organization.

The shop holds agent packs, built per queue — your words: a bookings pack works for an ocean liner and a freight forwarder alike. You can attach it to any org that runs that process.

The shop feeds assembly. A ready-made agentic system is piped into an organization while it is assembled — the way in. The finished assembly is what the Command's CI/CD commits to that customer's branch and ships to a UAT — the way out. A pack is never hand-carried: it flows in from the shop and out through the pipeline you already have.

  • A pack's card shows measured numbers: how often it is right, how much it raises the straight-through rate, cost per case, worst-case speed, and which orgs run it today. Not marketing text.
  • Attaching a pack to an org is done on the canvas: pick the org, pick the queue and sub-queues, set that org's thresholds. Minutes, not a project.
  • Versions never change after publishing. An upgrade is a new version with its own scorecard. You can run two versions on the same case, side by side, before switching.
  • Also important: every case a person completes in HITL becomes a stored example with a known correct answer. These examples are what scorecards are built from. Collection starts on day one.
Challenge 06

Input, output, rules, tools — and telemetry that cannot be forgotten

You askedThe ability to define input, output, rules, tools for an agent — with OpenTelemetry by default.

All five are defined in the manifest, using the org's own field names:

whathow it is defined
Inputwhich task fields the agent may read — these point at the org's existing field schemas, nothing new is invented
Outputwhich fields it fills in, and the minimum confidence needed on each field before "done" counts
Rulesrule sets and validation sets from the engines the org already runs. Rules are never copied into agent code. One rulebook, used by agents and people alike
Toolsa named list. The MCP gateway blocks any tool not on the list. But the agent alone decides which listed tools to use, when, and how often
Telemetryon by default, produced by the engine itself — the agent developer cannot forget it or turn it off. The manifest only adds extra fields and redaction rules on top
Challenge 07

One engine for both sides — and how it is packaged

You askedHow do we package agentic in the client runtime? I want engine-based. Can one engine work for both Command and client?

Yes. One engine, one repo, several parts — the same shape as your other engines:

contractthe manifest format, the run events, the connection, the access pass — and the presentation definitions: how a run reads as plain sentences, how a pipeline draws, the connection words. Small. Fixed early. This is the only part both sides must agree on.both

The engine is the definition centre — and nothing else. It ships pure capability and pure presentation definitions: schemas, the sentences a timeline reads as, the words on a connection, the shape of a pipeline graph, the fit-checks. It ships no React, no framework, no screen. The screens live in the web apps — Command and the client runtime — and comply with those definitions. The test for anything entering the engine: would a Vue, a Python, or a plain-CLI team want this exact package? If it only helps a React app, it belongs in the app, not the engine.

Packaging uses the machinery you already have: the runner and the gateway are containers in the org's bundle, listed in the engine manifest like every other engine. The org's agent packs travel inside the config bundle, stamped with the config generation, and are promoted from UAT to production unchanged.

Challenge 08

Where agents run — deployment targets

You askedHow will agentic really be deployed? Will it need its own target beyond the runtime's target? How is that set up in the Command?

One question decides it: where is this org's data allowed to be? There are three placements. All are set up in the Command's deployment targets — the existing target registry gets a role field (runtime / agent / both), and the org's deployment page gets a placement setting:

  1. 1

    Next to the runtime — extra containers on the org's existing target. This is the default. No data moves anywhere.

  2. 2

    Its own agent target — a second machine for the same org, defined in the Command like any other target. Used when agents need a GPU, different network rules, or would slow down the runtime under heavy load. So yes: an agent target can exist beyond the runtime's target, and setting it up is a page in the Command.

  3. 3

    A shared pool on our machines — only for agents that store nothing and touch nothing except an AI model.

The deployer already builds "only the containers this org needs". Agent containers are simply added to that list. Fixed rule: agents run where the org's data is allowed to be. The Command never receives case data.

Challenge 09

MCP — yes it is needed, and here is exactly how

You askedWill MCP be needed? Where are the MCP servers written? How are they packaged for the client? How do they emit telemetry? How do we define what telemetry each run emits?

Yes, MCP is needed — you were right. MCP is how an agent written in any language reaches data safely. And the key decision: we do not write MCP servers one by one. We build one gateway, and its tools are generated automatically.

  • Where it is written: once, inside the agent engine — the gateway part. Not per customer. Not per queue.
  • How it is packaged: one container in the org's bundle, like every other engine container.
  • Where its tools come from: generated from what the org already has — its queues and fields, its deployed engines (rules, validation, integration, extraction), its configured Integrations. Add a new Integration to the org, and the gateway gets a new tool. No code written.
  • Security: an agent never holds a password or key. For each run it gets a short-lived access pass: one org, one task, the named tools, valid for minutes. Nothing else is reachable.
  • Telemetry from the gateway: the gateway records and times every tool call itself. So you see exactly what an agent touched, even if the agent's code is badly written.
  • Per-run telemetry: defined in the manifest — which extra fields to record, what percentage of runs keep a full trace, which values must be redacted before writing. All configurable.
Challenge 10

Retries, timeouts, resumption, long-running agents

You askedHow do we handle retries, timeouts, resumption, long-running agents? Engine-based, everything configurable.

All of this lives in the runner, not in agent code. Agents stay simple; the engine handles the hard parts:

  • Retries are configured, and split by type of failure. A network error or a dead AI endpoint is worth retrying. A wrong answer is not — retrying it costs money and still gives a wrong answer. The manifest states which failure types get retried, how many times, and with what delay.
  • Three limits per run: a timeout per step, a total time limit, and a money limit. Hitting any limit is a normal ending, not a crash — the case goes to a person. Same principle as "never silently guess": never silently overspend.
  • Resumption: every step is written to the event log before the next step starts — the model's reply, the tool's reply, the time. If a machine dies mid-run, the run continues from the last written step. Any old run can also be replayed exactly, which means "why did it do that?" always has an answer.
  • Long-running agents: the agent ends with parked and states what should wake it — a reply, a document, a date. This uses the existing PARKED task state. No new system is invented.

Every number above is a manifest field, and each org can override it. Nothing is hard-coded.

Challenge 11

The AI provider

You askedThe AI provider they use can come from Integrations for that client or org.

Exactly that. The AI provider is an Integration, set per org — configured once, key stored as a vault reference. A pack never names a provider; it uses "this org's AI provider". Changing providers or rotating a key is an Integrations action. No agent changes needed.

Challenge 12

The UI

You askedHow are new agents created? How are they modified? How do we see the shop? How do we design observability on the client, and the channel that sends agent health and metrics back? Human-centered and top quality.

The center of the UI: one pipeline diagram, used in three places. The same diagram of a queue's pipeline appears three times and always means the same thing:

  1. 1

    Design — in the Command. Editable. Drag agents in, draw connections. A connection that does not fit (wrong field types) is refused immediately.

  2. 2

    Test — in the Command, running against the customer's UAT. The same diagram replays one real case. Each agent lights up as it works, showing what it read, what it decided, and what it cost.

  3. 3

    Monitor — in the client runtime. The same diagram, live. Case volume moving along the connections. Problems highlighted. This is the client-side monitoring screen.

Learn the diagram once, and you understand all three screens. Around it:

  • Creating and modifying agents: the Studio (Challenge 02). Modifying = open the agent, change it, save as a new version, test it, publish it. Published versions never change.
  • The run timeline: every run, ever, can be opened as a timeline and stepped through — what the agent read, what it decided, which tools it called, what it cost. Every run is recorded, so every run can be reviewed, forever.
  • The shop: pack cards with measured numbers (Challenge 05), one click away when assembling an org.
  • The health channel back to the Command: the runtime already sends regular status updates to the Command. Agent health data rides on that same channel — counts, durations, costs, decisions, error types, broken down by org, queue, agent and version. The Command shows all customers' agent health on one screen. Case data never travels on this channel. Full run details stay on the client's machine, where the client's own team can see everything.
  • Simple words, enforced: the UI never shows framework terms. Not "LangGraph node" — "step". Not "MCP tool invocation" — "looked up the customer's rate card". Every agent and every tool must have a plain-language label in its manifest — the manifest is rejected without one. The technical name is one click deeper for whoever wants it.
  • Where the screens live: in the web apps, not the engine. The engine defines what a run reads as and how a pipeline draws (Challenge 07's presentation definitions); Command and the runtime paint those definitions with their own components. So the diagram and the timeline read identically in both apps — same words, same fit-checks — because both comply with one definition, not because they share one React bundle. A screen can be rebuilt in any framework without touching the engine.
Challenge 13

Future frameworks — and Camunda

You askedHow do we make sure completely new frameworks can easily be used in the future? And if a customer insists on their own workflow engine, like Camunda?

A new framework = a new adapter. The contract does not change; the adapter translates. A framework that does not exist yet will cost one adapter when it appears — days of work, not a rewrite. This is what Challenge 01's decision buys permanently.

Camunda is also an adapter. A customer who insists gets an adapter that maps their workflow onto Malkom's pipeline steps. Their engine controls the order of the steps. But four things always stay with Malkom:

  • the manifest and the four endings
  • the gateway and the per-run access pass — their workflow never gives an agent a credential
  • the telemetry format
  • the routing to your HITL queue, with work attached

They control the sequence. Malkom keeps the rules, the security, and the audit trail.

Challenge 14

Human-centered and simple — how, exactly

You askedEverything in the UI developed and tested in a human-centered, simple, easy-to-understand way — how can that be achieved?
  • One diagram, learned once — the three-place pipeline diagram means nobody has to learn three different tools.
  • The simple-words rule is enforced by the software, not by good intentions — a manifest without plain-language labels is rejected.
  • Agent questions must be quick to answer. When an agent asks a question, the format is forced: one sentence, two to five choices, and the field the answer fills. Answering takes seconds.
  • Every screen answers exactly one question. The pipeline diagram: "is my queue healthy?" The run timeline: "why did it do that?" The shop: "is this pack good?" If a screen starts answering two questions, it becomes two screens.
  • Test with real users, every sprint. An operations person who has never seen Malkom works a real task while we watch. Every place they hesitate becomes the next fix. This repeats forever.
Build order

The order of work

Five stages. Each stage produces something that runs, and each builds on the previous one.

  1. 1

    Core. The contract, the runner, the gateway. One real autonomous agent on one queue, on one org's UAT, using all four endings, with HITL handover carrying its work. This proves Rule 1 works end to end.

  2. 2

    Studio and canvas. Agent development inside the Command. Build a second agent entirely in the browser to prove it.

  3. 3

    Testing and shop. Replay, shadow and canary on UAT. Scorecards. The promotion gate. The shop with measured numbers on the cards.

  4. 4

    Monitoring. The live pipeline diagram in the client runtime, the run timeline, and agent health flowing back to the Command.

  5. 5

    Adapters and agent targets. The LangGraph adapter proves any framework can be used. The Camunda adapter proves a customer's workflow engine can be integrated. Separate agent targets for heavy packs.

Summary: agents decide their own steps, inside fixed limits. They are built in the Command, run in the client runtime, and reach production only after passing tests on the customer's own UAT. That is the whole plan.
