Building on the Agent Engine

00The one idea

The engine is the definition centre — and nothing else

Everything below follows from one decision. The engine ships pure capability and pure definitions: the manifest format, the run events, the fit-checks, the sentences a run reads as, the words on a connection, the shape of a pipeline graph. It ships no React, no framework, no screen, and it never learns which AI model it is talking to or which machine it runs on.

The screens live here, in Command and the runtime, and comply with those definitions. That is the whole contract between you and the engine.

The litmus test for anything you are tempted to push into the engine: would a Vue team, a Python team, or a plain-CLI team want this exact package? If it only helps a React app, it belongs in the app. If it only helps your host, it belongs behind the seam. The engine stays the part everyone can share.

Three rules the vision rests on

  1. Testing never happens in the factory that builds. The Command builds agents; it does not "broadly test" them inside itself. Real testing is a deployed, running client runtime, reached through the CI/CD you already have — a customer branch to UAT, promoted to production only with Command CI/CD approval. Nothing reaches production silently.
  2. Everything flows to Malkom's own UAT first. Malkom's own UAT / Demo bears every agent before any client sees it. Only then does an agent travel to a customer's own UAT. Two test places, in that order — never the customer first.
  3. Real plumbing from day one. No fake doors. The in-process sandbox run stays for the one-click studio preview, but it stops standing in for real pipes — the integration hub, the gateway tools, and the pre-built MCP servers are the doors from the start, in the studio and in the runtime alike.
01What the engine is

One engine, six parts, one seam

One repo, the same shape as every other Malkom engine. You will import from these packages; you will never fork them. The two columns that matter to you: what it defines and what you must supply.

02Exposes · Consumes · Emits

The three verbs

The clearest way to hold the engine in your head. It exposes definitions and functions you call, it consumes exactly one thing you implement, and it emits a run's whole truth.

exposes

Definitions & pure functions

Schemas, fit-checks, and the presentation defs. You import and call. No state, no I/O.

consumes

One seam: HostIntegration

The real world, handed in: the model, the tools, the event sink, the adapters. The engine asks; you answer.

emits

The event log & telemetry

Every step written before the next begins. Four endings out. OpenTelemetry, produced by the engine, un-forgettable.

Exposes import from the packages

The presentation defs are the ones your UI leans on hardest — they are the engine telling you, framework-free, exactly how a run should read and how a pipeline should draw:

exportfromwhat it gives the UI
timelineLines()contractRun events in, an array of plain-language TimelineLines out — the sentence, the time, whether it is an accent line, the raw event for one-click-deeper. All the "how a run reads" logic. Your component only paints.
CONNECTION_WORDScontractThe words a pipeline wire means — hands the case to / may ask for help. Never invent your own labels.
pipelineGraph() · packGraph()contractAgents + connections in, a PipelineGraph of nodes and edges out. The one diagram, defined once, drawn in all three places.
ENDING_SENTENCEcontractThe plain sentence for each of the four endings.
checkAgentFit() · checkConnection() · assemblePack()studioThe canvas brain. A connection that does not fit is refused with sentences, before it is drawn. assemblePack turns a canvas into the pack that travels in the config bundle.
templateManifest() · templateCode() · compareVersions() · checkPublish()studioNew-agent scaffolding and the version rules. Published versions never change.
parseManifest() · parsePack() · checkPass()contractValidation you run on both sides. The Command validates a manifest before publish; the runtime checks the pass on every call.

Consumes you implement this

The engine reaches the real world through exactly one interface. Implement it once per host. The engine never learns the model's name, the machine, or the deployment — it only asks these questions:

interface HostIntegration {
  // The org's AI provider for this agent — an opaque handle plus prices.
  provider(agent: { id: string; version: string }): OrgAiProvider | Promise<…>;

  // The gateway tools this agent may use — YOU generate them from org config.
  tools(agent: Manifest): readonly GatewayTool[] | Promise<…>;

  // Where a run event is written, before the next step starts. Resume & replay.
  keep(event: RunEvent): void | Promise<void>;

  // The framework adapters installed on this host.
  readonly adapters: AdapterRegistry;

  now?(): number;   // optional clock
}

Then you call one function. In the runtime today, that call is already wired — treat it as the template:

const report = await runPipeline(
  { pack, caseRecord, resume },              // the request: what to run
  { provider: () => aiProvider,              // the seam: the real world
    tools: (manifest) => toolsFor(task, manifest),
    keep, adapters },
);

The one line to never cross: OrgAiProvider.model is typed unknown on purpose. The contract does not know what a model is; only the adapter that starts the agent does. Keep it that way — the moment the engine "knows" it is Claude or GPT, it stops being the definition centre.

Emits the run's whole truth

  • The event log — runStarted, modelReplied, toolCalled, toolReplied, noted, runRetried, runEnded. Gapless and ordered: every step is handed to keep() before the next begins, which is what makes resume-after-crash and exact replay possible. checkEventLog(), resumePoint() and spendOf() read it back.
  • The four endings — done, question, handover, parked. needsAPerson() tells you which ones land a human in the loop. A handover carries its work with it.
  • OpenTelemetry — produced by the runner itself (startRunSpan, recordEventOnSpan, closeRunSpan). It cannot be turned off or forgotten by a badly-written agent, because the engine emits it, not the agent.

request pipe: the host builds a Start — goal, case narrowed to the fields the manifest may read, the access pass, the offered tools, the limits, the provider. report pipe: every report(event) flows to keep(); every call(tool, args) flows through the gateway and back as a ToolReply.

  • The access pass — one org, one task, the named tools, valid for minutes. An agent never holds a password. The gateway checks the pass on every single call; anything not on it is refused, recorded, and the reason returned.
  • The gateway's tools — generated by toolsFromOrgConfig() from what the org already has: its queues and fields, its deployed engines (rules, validation, extraction), its configured Integrations. Add an Integration to the org, and a new tool appears. No code written per customer.
04The agentic builder

Building the builder, in Command

This is the biggest piece of new UI, and there is a working reference to build against — the studio and canvas already shipped in command/apps/web/src/features/agent-studio. Read them as the pattern, then take them further. The shape, screen by screen:

The Studio — create, modify, version

  • New agent from templateManifest() + templateCode(), seeded by the queue it is for.
  • Editing is a code surface (CodeMirror in the reference) plus the manifest form. Modify = open, change, save as a new version, test, publish. Published versions never change — compareVersions() and nextVersion() hold that line, checkPublish() guards the gate.
  • Every agent and every tool must carry a plain-language label, or the manifest is rejected. The UI never shows a framework term.

The Canvas — the pipeline for a queue and its sub-queues

  • Place published agents on a queue; draw connections between them. A sub-queue can override the queue's pipeline — the same override pattern Malkom uses everywhere.
  • Every connection is checked by checkConnection() before it is drawn; a mismatch is refused with plain sentences. Draw the wires with pipelineGraph() and label them from CONNECTION_WORDS — never hand-written strings. The reference uses @xyflow/react, deduped host-side; you are free to choose otherwise, as long as the words and fit-checks come from the engine.
  • Save calls assemblePack(). The pack is what the config bundle carries.

The Run button — the sandbox preview

  • One click runs the draft on a sample case through the real runner and gateway; every step streams into the timeline, live. This is the one place the in-process run stays.
  • Without a configured provider, sandboxModel() (from adapters) stands in so the draft still runs end-to-end. The moment a provider is configured, the same draft runs against the real model — nothing else changes. Remember rule three: this preview is a convenience, not a substitute for testing on a deployed runtime.

The Shop — pack cards, measured

Published packs become cards with measured numbers, one click away when assembling an org. This is the head of the build-and-ship pipe in section 03.

05Integration manager

Wiring the integration manager

The gateway is where the vision's "deep integration hub from day one" becomes real. It is written once, inside the engine; your job on the host is to feed it the org's world and answer its data-door questions.

Generate the tools from org config

Call toolsFromOrgConfig(config, host). The config is the org's fields and configured Integrations; every entry becomes a named, labelled, schema'd tool the agent can be offered. Adding an Integration in the integration manager is adding a tool — that is the whole point, and it is why no MCP server is written per customer.

Answer the data doors — the GatewayHost

The engine defines the doors; you implement the ones this host has. Each is optional, so a host wires only what it can reach:

interface GatewayHost {
  readCase?(): Promise<unknown>;
  writeFields?(a: { fields; confidence }): Promise<unknown>;
  checkRules?(a: { ruleSet; fields }): Promise<unknown>;
  checkValidation?(a: { fields }): Promise<unknown>;
  extractFields?(a: { text }): Promise<unknown>;
  callIntegration?(name, args): Promise<unknown>;   // any configured Integration, by name
}
  • Pre-built MCP servers — the gateway can also expose itself as an MCP server via mcpGateway(), so an agent in any language reaches the same doors, with the same pass check and the same recording. Build these once, per capability, not per customer.
  • Redaction — redactorFor() honours the manifest's telemetry rules, so values that must not be written are stripped before they reach the log.
06Deployment targets

Deployment targets via the assembler

One question decides where an agent runs: where is this org's data allowed to be? The engine has no opinion; the assembler and the Command's target registry carry it. Add a role to a target (runtime / agent / both) and a placement to the org's deployment page:

  1. Next to the runtime — extra containers on the org's existing target. The default. No data moves.
  2. Its own agent target — a second machine for the same org, defined in the Command like any target. For a GPU, different network rules, or heavy load.
  3. A shared pool on Malkom's machines — only for agents that store nothing and touch nothing except an AI model.

The assembler already builds "only the containers this org needs". The runner and the gateway are two more containers in that list, and the org's packs travel inside the config bundle it produces. Nothing new is invented — agent containers are added to the same build the deployer already does.

Fixed rule, non-negotiable: agents run where the org's data is allowed to be, and the Command never receives case data. Only health metrics ride the channel home.

07UI specifications

The UI, specified — not prescribed

The engine tells you what a screen must say and which logic it must obey. It does not tell you the framework, the components, or the pixels. What follows is the binding half; the rest is yours.

One diagram, three places

The same pipeline diagram appears three times and always means the same thing. Build it once, from pipelineGraph(), and reuse it:

placewherestate
DesignCommandEditable. Drag agents in, draw connections. A misfit is refused immediately.
TestCommand → client UATThe same diagram replays one real case. Each agent lights up: what it read, decided, cost.
MonitorClient runtimeThe same diagram, live. Case volume along the wires; problems highlighted.

What your UI must obey

bind to the engine
  • Render the timeline from timelineLines() — paint the sentences, don't compose them.
  • Label wires from CONNECTION_WORDS; draw them from pipelineGraph().
  • Refuse connections with checkConnection() before drawing.
  • Show the four endings with ENDING_SENTENCE.
  • The technical name is always one click deeper, never the first thing shown.
never do
  • Never write your own connection words, ending text, or "how a run reads" logic — that is the engine's to define.
  • Never show a framework term: "step", not "LangGraph node"; the tool's label, not "MCP invocation".
  • Never put case data on the health channel or anywhere near the Command.
  • Never let a manifest without plain-language labels reach publish.

The health screen

The runtime already sends status home; agent health rides that same channel — counts, durations, costs, decisions, error types, by org, queue, agent and version. The Command shows every customer's agent health on one screen. Full run detail stays on the client's machine, for the client's own team.

The visual bar — build screens people trust

The engine sets what a screen says. This is the bar for how it should look. It is not a style guide to invent — the whole point is the opposite: honour the host's own design system first. Command already ships one — design tokens (surface, border, muted, a single accent), a component set (Card, Button, Badge, Input), and utilities (uppercase tracked labels, tabular numbers, themes). Use it. A studio screen should be indistinguishable in craft from the rest of Command. Never hand-roll a colour, a font, or a one-off bordered box when a token or a component exists.

the bar to hit
  • Real hierarchy. Every screen opens with an eyebrow label, one clear title, and a one-line purpose — then the content. Size and weight carry importance; not everything is the same 14px.
  • Let layout breathe. Space with grid/flex gaps on a consistent rhythm; group related things, separate unrelated ones. Cramped is the tell of an unfinished screen.
  • Cards, not bare boxes. Use the host's Card for grouped content; give lists a hover and a focus state, and interactive things that look interactive.
  • Every state designed. Empty (a real first-run panel with a way forward), loading, and error each get a considered treatment — not a blank space or a raw message.
  • Status reads at a glance. Semantic colour (ok / pending / failed) is separate from the accent; a badge or chip encodes state so it is scannable, and numbers line up (tabular).
  • Plain words on top, detail one click deeper — the same rule the engine enforces, made visual: the sentence is the surface; the technical name is a click away.
  • Both themes, always. Style through tokens so light, dark and any brand theme all hold; never a literal colour that only works in one.
the "unfinished" smells
  • Flat bordered <div>s everywhere, all the same weight and spacing.
  • No empty state; a blank panel on first run.
  • A hard-coded hex or font instead of a token — it breaks the moment the theme changes.
  • Raw identifiers or framework terms shown to an operator.
  • Controls with no hover, no focus ring, no disabled/busy state.
  • "It works" treated as "it's done." Functional is the floor, not the bar.

Rule of thumb: a screen is finished when an operator who has never seen Malkom can look at it once and know what it is, what matters on it, and what to do next — and when it sits beside the rest of Command without looking like a different product.

Reference implementations to read, not to copy verbatim: RunTimeline.tsx and PipelineCanvas.tsx in command/apps/web/.../agent-studio/components. They already render entirely from the presentation defs — proof the seam holds. The Agent Studio pages in the same feature folder are the reference for the visual bar above.

08Guidelines, abstract

How to build on it — for both sides

Deliberately non-prescriptive. These are the boundaries that keep the whole thing coherent; the design inside them is yours to make.

For the Command

  • You are the factory: build, version, assemble, publish, watch. You never run a customer's real cases and you never hold their case data.
  • Every screen that describes a run or a pipeline reads from the engine's presentation defs. When you want it to say something new, add the definition to contract — do not hard-code the sentence in a component.
  • Keep the sandbox preview honest: it is a preview, and the word "tested" belongs to a deployed runtime, not to it.

For the runtime

  • You are the only place real cases run. Implement HostIntegration and GatewayHost for your world; keep the model handle opaque.
  • Write every event through keep() before the next step — resume and replay depend on it. Let the runner produce telemetry; do not roll your own.
  • Send health home; keep case data local. That single boundary is what lets one Command watch many clients safely.

For both

  • Import the engine; never fork it. A gap in the engine is fixed in the engine, at the pinned commit, then re-vendored — not patched in a host.
  • A new framework is a new adapter, not a new engine. When one appears, it costs one adapter.
  • When in doubt, apply the litmus test from section 00. If a thing only serves one host or one framework, it does not go in the engine.
09Where to start

The order of work

You are not starting from zero. Shipped and proven: the engine wired into the real runtime with one autonomous agent ending all four ways; the studio and canvas, with a second agent built entirely in the browser; both day-one adapters (TypeScript and LangGraph/Python); and the gateway's rules door and integration door wired to the real engines. A sensible path from here:

  1. Read the reference. The studio, canvas, RunTimeline and PipelineCanvas already in command/apps/web, and the runtime's engine.ts wiring of HostIntegration. They are the working template for everything above.
  2. Make the pipes real, one at a time. Section 03 is the checklist. Start with the shop → assembly → config bundle path, since it is the spine of every deployment.
  3. Grow the integration manager. Each new door in GatewayHost and each pre-built MCP server widens what agents can safely touch — the deep hub, filled in over time.
  4. Build the three-places diagram once. Design, Test, Monitor from one pipelineGraph(). Learn it once, understand all three screens.
  5. Then the health screen, closing the loop from a running client back to one Command.

Everything in this document is drawn from the engine as it actually stands — the exports, the seam, and the wiring are real and shipped, not aspirational. Build against them directly. Where you need the engine to do something new, the answer is almost always a new definition in contract, not new logic in a host.
